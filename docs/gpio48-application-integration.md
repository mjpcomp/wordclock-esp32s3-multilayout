# GPIO48 application integration candidate

Baseline: feea7108642a0ed1d3797ccff174b69151ffd8f5. Continues gpio48-runtime-validation.md.

This candidate adds a single-TU application adapter and a guarded integration workflow. The workflow transforms only src/WordClock.cpp and .github/workflows/isolated-build.yml after checking its parent and exact input file list. Missing/duplicate/already-applied anchors refuse the edit. It runs all twelve host suites and compiles both isolated profiles before an automatic follow-up commit of those two files. It refuses to push if the branch moved. A failed run must be investigated; do not mark integration complete merely because the preparation commit landed.

Hooks: include the adapter after activeLedStrip; reset frame tracking before backend deletion; forward valid ESP32 SNTP notifications with millis timestamps; record RTC source only after successful settimeofday with a valid epoch; service before network setup and after clockWork.loop. Normal-mode methods are no-ops. The isolated instance derives RTC expectation from MODE==2 and sends only through Gpio48Sink. AP mode is observed from WiFi mode, connectivity from WL_CONNECTED; Connecting is asserted only around the actual network.setup call. Unexpected physical backends select the model fault state.

Known limitation: existing WiFiManager setup/portal calls and other application work can block the main task. This change does not promise continuous breathing/blinking during those stalls. It deliberately does not switch portal mode, move web-server startup or add a background GPIO task. Nonblocking portal conversion needs separate review of HTTP port ownership. Once the main loop runs, existing workload still determines service cadence; 20ms in the sink is a rate limit, not a guaranteed schedule.

Local validation: the integration script self-test passed on minimal anchor fixtures, checking successful edits and refusal of repeats/missing/duplicate anchors. A separate local g++ C++11 warnings-as-errors/sanitized fixture compiled adapter modes 0/1/2 using mock policy/runtime/sink interfaces and checked normal dependency exclusion, AP priority, explicit connection-attempt state, counter/fault gating and event forwarding. No local full checkout, real-dependency adapter compile, target build or hardware validation has occurred. The remote workflow is the acceptance gate. Existing sink/runtime tests use mocks and do not prove physical output or multi-producer correctness.

Evidence: manifests describe the preparation commit with tracked working-tree integration changes. The workflow preserves the tested patch and resulting follow-up commit ID to connect that candidate to its committed tree. Do not describe manifests as clean builds of the follow-up SHA. GitHub-token pushes may not trigger another workflow; both target builds are therefore run explicitly before the follow-up commit. No flash-readiness claim.

Next: inspect workflow results and build provenance, resolve any test/compile failures, validate RGB mapping and main-loop patterns on the board, then address blocking-portal diagnostics if required. No soldering or external wiring prerequisite.
